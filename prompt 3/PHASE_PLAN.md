# Shared Phased Work Plan — Parallel but Gated

The agents work in parallel only on their assigned areas. They do not rush through the project in a single run. Each phase ends with a report and a stop for the owner's approval.

## Phase 0 — Concurrent audit only (no source changes)

**Codex:** inspect app architecture, X-Ray Workspace state/file lifecycle, viewer/GLB-loading patterns, tests, root README consistency, and minimum changes. Create `CODEX_STATUS.md`.

**Antigravity:** verify model candidates, checkpoint availability, license/usage terms, inputs, output/coordinate handling, hardware feasibility, and minimal inference path. Create `ANTIGRAVITY_STATUS.md`.

**Gate 0:** owner reviews both reports. If a real checkpoint is not currently available, the team can still build UI/API infrastructure that truthfully reports unavailable; do not claim inference works.

## Phase 1 — Stabilize foundations (parallel after approval)

**Codex:** make only necessary improvements to existing AP/lateral upload validation, preview/replacement/removal, local object URL cleanup, and empty/error states. Preserve brightness, contrast, zoom, pan, rotation, fit/reset, and sample loading. Keep backend transmission off until explicit reconstruct click. Do not add new state persistence.

**Antigravity:** create minimal isolated FastAPI service under `xray-reconstruction-service/`, health/capabilities endpoints, config, upload validation skeleton, and tests. Until a compatible verified checkpoint is configured, capabilities must say unavailable.

**Gate 1:** run relevant frontend and backend checks. Confirm existing main anatomy, Muscle, Neuro, Spine, X-Ray, Stress, navigation, theme, and exports have not regressed.

## Phase 2 — Capability and model proof (parallel after approval)

**Codex:** build a typed API client and capability-driven UI states using the fixed API contract. Keep the reconstruction target list separate from the existing manual atlas-association selector / `stressTargetId`. Display only anatomy labels actually returned by the backend. Use mocked tests while backend inference is under research.

**Antigravity:** obtain and verify the candidate checkpoint only if permitted; reproduce one documented supported example using the upstream preprocessing and sample data. Establish exact anatomy labels, orientation, output tensor/label semantics, coordinate system, and hardware needs. Do not train unless separately approved.

**Gate 2:** compare the real checkpoint's supported target and inputs against the API/UI. If no compatible checkpoint can run, report the blocker and ask whether to continue only with truthful scaffold/API work or evaluate a different model. Do not advertise capabilities unsupported by a verified checkpoint.

## Phase 3 — Real inference output and job integration (parallel after approval)

**Codex:** implement job submission/polling/cancellation/timeout and error presentation against the fixed endpoints. Never fabricate progress. Handle unsupported targets and unavailable models explicitly.

**Antigravity:** implement the verified inference adapter and correct output-to-mesh conversion if model output permits it. Add job state, result route, safe temporary paths, cleanup, and GLB validation. If the model is still blocked, do not replace it with fake inference.

**Gate 3:** test shared API request/response behavior. A test fixture may test plumbing only if clearly identified as a fixture. It cannot be presented as an X-ray inference result.

## Phase 4 — GLB viewer integration (parallel after approval)

**Codex:** reuse existing GLB viewer patterns or create a small result-only preview. The generated result must not replace `public/anatomy/skeletal_male.glb` or mutate atlas state. Add loading, error, camera reset, and download for a valid output.

**Antigravity:** serve the actual generated GLB only for successful jobs, with the correct content type and job ownership/existence checks.

**Gate 4:** verify the actual result URL reaches the viewer and that the model shown is the file generated by that job. Test errors and cleanup.

## Phase 5 — Full regression and handoff (parallel after approval)

**Codex:** run `npm run build` and `npm run test:e2e` where the environment supports them, plus relevant checks. Confirm existing features remain functional; document exact setup steps.

**Antigravity:** run backend unit/API tests; if possible run a real checkpoint-dependent test explicitly. Document setup, checkpoint provenance/license, hardware requirements, and limits.

**Final Gate:** the owner verifies both status reports and the actual end-to-end path. Do not report full reconstruction success without inference on a supported input pair and successful loading of the resulting GLB.

## Stop/report format after every phase

Each agent's status file must state:

- Phase and date/time.
- Audit-only or implementation summary.
- Files changed.
- Commands and tests executed, exact pass/fail outcomes.
- What is verified working versus mocked or not verified.
- Blockers/risks and decisions needed.
- Next phase proposed.
- Confirmation the other agent's owned files were not modified.

## Repository safety

- Inspect `git status` before and after each phase.
- Do not run `git reset --hard`, destructive clean commands, or blindly restore files.
- Do not commit, merge, push, or alter unrelated user changes unless the owner requests it.
- If agents use separate workspaces, the status files are not magically shared; exchange reports/patches manually before integration.
